# V1.1 Stage-A core evaluation

Stage A asks whether the fixed-window JEPA representation contains stable future-relevant information on unseen, later real-contract groups. GO requires temporal isolation, nontrivial latent health, OOS JEPA prediction, and a frozen Ridge probe outperforming the causal MultiScaleSummary baseline. It does not establish an identified Predictive State, trading value, RSSM value, or unseen-commodity generalization.

## Training split and provenance

After existing history, bar, and dataset eligibility gates, each commodity's `(commodity, contract_uid)` groups are ordered by earliest main-start, breaking ties by contract UID. All re-main episodes remain together. For `n >= 3`, Fit has `min(max(1, floor(.70*n)), n-2)` groups; Dev has `min(max(1, floor(.15*n)), n-fit-1)`; Test is the remaining latest suffix. Fewer than three groups excludes the commodity from formal Stage-A aggregation, with reason `insufficient_contract_groups`; its eligible contracts may still train.

The runner writes an immutable `stage_a_temporal_split.json` before scaler fitting. Sampler and shared scaler both use a dataset view that excludes Test contract groups. Raw history, lineage, IMC, targets and model math retain their existing construction. To enforce temporal isolation when lifecycles overlap, training anchors whose H256 target reaches the first Test main-start are also excluded. If a Test contract appears in an earlier training episode's historical weekly source, preflight blocks for review rather than silently changing lineage/stitching. An empty resulting training commodity also blocks.

Checkpoint metadata binds the complete split, split SHA256, restricted sampling population SHA256, training contract identities and actual selected scaler anchors. Resume rebuilds and compares the immutable split; Stage-A evaluation checks the file against the checkpoint and independently reconstructs the restricted population. `data_audit.json` and `protocol.json` include the formal commodities, Test contract counts and zero Test sampler/scaler selections. Actual commodity counts and split SHA are dataset-dependent and are generated by preflight, not invented in this document.

All profiles inherit `evaluation.stage_a_temporal_oos` from the base YAML. Formal training requires its reviewed configuration. Scheme A remains 250,000 successful optimizer updates, warmup 12,500, effective batch 128 and 32,000,000 selections. Model, objective, BF16 and optimizer settings are unchanged. Existing checkpoints lacking temporal binding remain available to extended diagnostic evaluation but receive `STAGE_A_BLOCKED_LEGACY_CHECKPOINT_NO_TEMPORAL_HOLDOUT` from `stage-a`.

## Core audit

The audit loads Full S and the checkpoint-bound split; it never re-splits contracts. Each Fit/Dev/Test partition has a cap of 4096 anchors per commodity, sampled deterministically without replacement using contract-day round-robin pools. Re-main duplicate raw anchors are included once. `evaluation_manifest.json` records the split, data and anchor identities with its own SHA256.

A0 saves ProbeTest belief and H16/H64/H256 EMA latents in `a0_probe_test_latents.npz`, with aligned identities in `extraction_records.json`. It reports variance, covariance eigenvalues, numerical/effective rank, participation ratio and raw/centered cosine. Numerical conventions: at least three samples (the minimum for centered rank two), variance epsilon `1e-12`, eigenvalue rank threshold `lambda_max * 1e-6`. Nonfinite values, insufficient samples, trivial variance or rank below two block. Effective-rank ratio below .05 and raw cosine above .99 only warn. Cosine means use at most 4096 deterministic samples and an algebraic off-diagonal sum without allocating an N-by-N matrix.

A1 compares future JEPA predictions against horizon-specific trailing-H EMA persistence, ProbeFit mean target and deterministic seed42 ProbeFit target shuffle. Future targets retain online same-origin IMC. Only ProbeTest errors enter formal metrics. A2 reuses the existing V0-exact 12 outcomes, Ridge alpha grid, Fit-only normalizers, Dev alpha selection and Fit+Dev refit. Primary baseline remains MultiScaleSummary plus causal context; unconditional, context and MinuteRaw24 baselines remain secondary.

Both primary gates require ALL lower 95% CI > 0, a positive lower bound at H64 or H256, and no strictly negative upper bound at either long horizon. A1 additionally requires positive aggregate lower bounds against mean and shuffle. Aggregate upper bound <= 0 or significant negative long-horizon evidence gives FAIL; otherwise insufficient positive evidence is INCONCLUSIVE. H16 is diagnostic. All CIs use 2000 seed42 paired `(contract_uid, trading_date)` block bootstrap replicates and equal commodity weighting.

`STAGE_A_GO` requires isolation/A0/A1/A2 PASS. Scientific negative evidence gives `STAGE_A_NO_GO`; uncertain predictive evidence gives `STAGE_A_INCONCLUSIVE`; provenance, leakage, nonfinite or collapse failures give `STAGE_A_BLOCKED`. Local `stage_a_summary.json` and `.md` are authoritative.

## Commands and migration

Start a new Full S run after code review; this development task does not launch it:

```bash
/home/v/Documents/work/market_jepa/.venv/bin/python train_market_jepa_v1_1.py \
  --config configs/v1_1/market_jepa_v1_1_s.yaml \
  --output artifacts/training/v1_1_stage_a_s
```

After its final endpoint completes:

```bash
/home/v/Documents/work/market_jepa/.venv/bin/python evaluate_market_jepa_v1_1.py stage-a \
  --checkpoint artifacts/training/v1_1_stage_a_s/checkpoints/last.pt \
  --output artifacts/evaluation/v1_1_stage_a_s \
  --device cuda --batch-size 8
```

Existing `train-domain`, `compare`, `freeze-rb`, `rb-dev` and `rb-test` remain POST_STAGE_A/extended commands. The Stage-A command does not invoke A3, source removal, controls, scaling, RB or kNN. It creates no RB consumption ledger. Optional W&B integration is not needed to calculate or interpret the local Stage-A gate; this initial core command writes local artifacts only.

The first real Stage-A result and actual formal/excluded commodity inventory require the new preflight and final checkpoint. Synthetic integration verifies the pipeline, not predictive success on production data.
